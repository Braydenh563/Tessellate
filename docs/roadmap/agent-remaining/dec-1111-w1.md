## B24: keep the citations

- Question: strip the 478 `INBOX n` / `decision n` markers (whiteboard.js 290 hits, whiteboard-map.js 115 by the `INBOX|decision <n>` pattern) or keep them.
- Options: (a) scripted strip of every marker, a 37k-line rewrite that collides with every other board worktree; (b) strip only bare markers that add no reason; (c) keep.
- Measured: whole-line markers with no reason beside them: 2 of 405 lines (`(MINDMAP_PLAN 20).` and `decision).`, both tails of a sentence that has its reason). The 188 `(INBOX n)` / `(decision n)` parentheticals each follow a stated reason (the owner's words or the measured cause). A scripted check found 0 of the 188 repeated in a test file as an anchor, so no test pins them, but they are the only trace from a rule in code to the owner's request, and `HISTORY.md` and the plans resolve the numbers.
- Recommendation: (c). CLAUDE.md section 7 says comments explain why; these do, and the number is the evidence for the why. Nothing "bare" exists to strip, so (b) is empty and (a) is risk for no reader gain. Rule going forward: cite one number beside its reason.

## B4: the dirty set is the paint key

- Question: the row says `wbScheduleRender` repaints the whole board with no dirty set and proposes a dirty-id set through every caller (L, over 150 lines).
- Finding: stale as written. Pen strokes were keyed in dec005f; shapes and connectors in 75e07d492 (W30 rest; a shape keys on data, id, ink and the rough default, a connector adds the ends it resolves to now); topics and objects have `wbObjectPaintKey`. A dirty-id set would need all 48+ callers to name what they touched, and a missed caller leaves a stale item; the key cannot go stale because it is computed from what the item draws from.
- Remaining cost on the current head, found by counting DOM writes with a MutationObserver on an unchanged board of 250 shapes, 250 strokes, 30 connectors: 1,060 writes per render, all `class` on `.sketch-group`, from two `sketchUpdate.classed(...)` calls per group (d3 re-sets the attribute even when the token is right).
- Built: `classIfChanged` (local to `renderWhiteboard`, so no new global name) writes a class only when it differs; test in `tests/test_wb_render_w30.py`.
- Measured (scratchpad w1/b4.js, board of 530 sketch groups, CPU throttled 4x, 20 renders, same session):
  - Unchanged board, DOM writes per 20 renders: 21,200 to 0.
  - Unchanged board, median render: 43.5 to 44.7 ms before, 27.6 to 32.5 ms after over three runs (the throttled median is noisy, the write count is exact).
  - Keys off (every group repainted), same board: 224.7 to 254.4 ms, 141,000 to 162,200 writes. The key is worth about 6 to 8 times.
  - Moving a connector's end object repainted that connector: path `M 60 20 L 90 20 ...` became `M 60 20 L 93.5 20 ...`.
- Not verified: 1x CPU numbers, a topic-heavy map after this change (the helper only touches sketches).
- CHANGELOG line: `Whiteboard: an unchanged board no longer rewrites its sketches' class attributes every render (530 sketches: 1,060 DOM writes per render to 0; render 44 to 28-33 ms at 4x CPU); audit 1028 B4 closed, the paint key is the dirty set.`

## B15: keep the one-line bridge

- Question: move d3.drag to pointer events so `new MouseEvent("mousemove", at)` (whiteboard.js, `wbEdgePanTick`) can go.
- Options: (a) hand-roll a pointer-event drag in place of `d3.drag()` at its 17 call sites, all in whiteboard.js; (b) keep d3-drag and the bridge.
- Measured: the vendored d3 v7 (`frontend/vendor/d3.v7.min.js`) listens for `mousemove.drag` (2 sites) and `touchmove.drag` (1 site) and has no pointer variant, so (a) replaces the library's drag rather than switching an option. The bridge is one call, handed straight to d3-drag's own `mousemove.drag` listener (B16 narrowed it so no other listener sees it), pinned by `tests/test_wb_edge_pan.py`. The only thing it carries is the held pointer position while the board pans under an edge drag.
- Recommendation: (b). A 17-site drag rewrite touches item, group, resize, rotate, link and sketch gestures, each with undo and snap behaviour; the sweep that proves it identical is larger than the line it removes, and the bridge now re-enters nothing.
- Taken as: closed, won't do. No code change, so no drag sweep was needed; re-open only if d3 is replaced.
