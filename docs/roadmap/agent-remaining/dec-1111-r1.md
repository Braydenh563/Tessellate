## E44: chatSendTurn

- Question: the function mixes the ask, the commit, the stream reader, the failure path, the paint, the settle and the
  persist in one closure of mutable `let`s.
- Options: (a) top-level functions (breaks the global-names ratchet, cap 9044 met exactly); (b) a class (new global,
  and a rewrite); (c) stages as properties of `chatSendTurn` with the turn's mutable state on one object.
- Recommendation: (c). Mutable `let`s became `t.X`; immutables are destructured from `t` per stage; `paint` stores
  `answerRaw, thinkingRaw, turnSources, elapsedMs, resumeState, model` on `t` for the later stages; the slow-load timer
  is `t.slowLoad`, cleared in `teardown`.
- Why: behaviour-preserving by construction (same order, same state), no new global, and each stage can be read alone.
- Verified: identical DOM and request bodies across four synthetic NDJSON streams (rich, asks, empty, error) against
  baselines saved before the split; send, Stop and regenerate driven in the running app on port 8798; an eslint
  `no-undef` diff between the original and new file as a free-variable check; 26 chat test files and 278 JS-reading
  test files. Not verified: tool-event handlers beyond the synthetic streams, and any real-model run (the standing
  caveat).
- Side effects: nine source-literal tests and fifteen test files follow the stage names (intent unchanged).
  `tests/test_undo_coverage.py` EXEMPT is shrink-only and grew by one: the undo wrapper call moved into the `ask`
  stage, so the exempt key is now `chat-turn.js:persist` where `chatSendTurn` was never exempt. Flag for the owner.
- CHANGELOG line: `E44: chatSendTurn (1,193 lines) is 29 lines; its stages (ask, commit, open, stream, fail, teardown, paint, settle, empty, persist, afterAnswer) live on chatSendTurn.stage, a pure move, same DOM and requests on four recorded streams.`

## E45: one AnswerStream consumer

- Question: should help-chat.js, agent-activity.js and chat-tasks.js read their streams through answer-kit.js
  `streamChatEvents`?
- Options: (a) migrate all three; (b) share a small NDJSON line reader; (c) close.
- Recommendation: (c).
- Why: `streamChatEvents` is the chat protocol (`answer.delta`, `thinking.delta`, `tool`, `meta`, and the stop and
  resume handling). Help chat sends `{type: "delta" | "thinking" | "done"}` with a `text` field and no tools or resume;
  the agent log stream is NDJSON `open` / `record` with a cursor and a reconnect loop; the jobs stream is SSE blocks
  (`event: runs` / `event: tasks`, split on a blank line, not NDJSON at all). Forcing them through the chat consumer
  would need a shape adapter for each, which is more code than the six-line read loop each one has, and the shared
  line reader would add a new global name when the cap is met exactly. The three readers also reconnect and cancel
  differently, so a shared one would carry three callbacks.
- Taken as: closed with this reason. No code change.
