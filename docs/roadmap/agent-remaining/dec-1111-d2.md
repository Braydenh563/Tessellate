# dec-1111-d2: audit-1028 row D22, split the `library` bundle into `library` (documents, list) and `boards`

Design is dec-1111-d1.md row D22: (b) two bundles with the same `lazyScript` dedupe so order holds, plus (c) a stand-in for each call the documents make into board code.

## What changed

- `library` (app.js) no longer lists d3 or the nine `whiteboard*.js` files. `boards` (lazy-entries.js) is `...LAZY_MODULES.library` then `/vendor/d3.v7.min.js` and the nine files, in their old order. A spread, so the two lists cannot drift; app.js (at its gzip cap) did not grow.
- Stand-ins, group `boards` (lazy-entries.js): `createNewBoard`, `openWhiteboardBoard`, `renderLibraryBoardsGallery`, `wbMapFromDocument`, `wbShowBoardsLanding`. They were `library`'s stand-ins before (minus `wbMapFromDocument`, which was a real function in the same bundle).
- Two names whose answer is read are not stand-ins; the caller tests `typeof`, which now means "no board is open": `wbEditorSurfaceById` (documents.js `docSurfaceById`), `wbCommandsLive` and `wbEditDiagram` (documents-mermaid.js `diagramDoor`).
- `wbToggleNavigator` and `wbOpenBoardSearch` lost their stand-ins (not needed: the Help targets call them after `await revealBoard()`, which awaits `ensureModule("boards")`; wiring.js calls the search only while a board canvas shows). That freed the bytes the boot ratchet needed (see Numbers).
- Doors changed from `ensureModule("library")` to `ensureModule("boards")`: library.js (New board, New mind map), navigation.js (dashboard `new-board` action), reveal-targets.js (`revealBoard`, `revealBoardsGallery`), search.js (board and map results), whiteboard-library.js (`wbLoadLibrary`), whiteboard.js (one site).
- The Boards sub-tab hover no longer warms the bundle (a `warmOnFirst` line was tried and dropped for the boot byte cap). `warmLibraryAfterInput` now warms graph and documents only; the first board costs its files on first use.
- Behaviour change, deliberate: palette rows from `mapPaletteCommands`, `wbPaletteCommands` and `wbPaletteActRow`, and the `wbOwnsChord` guards, only exist once boards is loaded. They act on an open board, so this loses nothing.

- **Reload after a gallery click restores the board.** Not reproduced: gallery card click, then reload at 0, 150, 500 and 700 ms and after 1.5 s, on this change's server, on the baseline (`cacee3142`) and on a fresh data dir where the board had never been opened: board 1 and `#/library/board/1` came back every time (6 runs). The earlier failure was most likely the check (a board id left over from a previous open, or read before the restore finished), not the app. Note the address is still `#/library/boards` for the first ~250 ms after the click, so a reload inside that window relies on the remembered board, not the address.
- **A real bug found on the attach-to path, fixed, and not from this split.** With the idle warm-up on (4+ cores, which the earlier sweeps switched off), the library bundle arrives one file at a time (`warmNext`). `documents-view.js` fetched `documents-ide.js` as it ran, which put the IDE file on the page before `documents.js` had run: `docToolPref is not defined` (documents-ide.js:186, so its setup stopped on its first line, no minimap) and `docCmView is not defined` (documents-view.js:204). Identical on the baseline (`cacee3142`), so it came with D21, and it is the failure the section above lists as "found, not fixed". Fix: `documents-view.js` fetches the IDE file once `documents.js` has loaded, and reads `docCmView` behind `typeof`. That also turns `test_lazy_order_1530.py::test_no_bundle_file_reads_a_later_file_after_an_await_without_the_bundle` green. New test: `test_code_ide_b42.py::test_the_ide_file_waits_for_documents_js_before_it_is_fetched`.
- **Reload leaves the same address twice in the browser's history** (the boot pushes one), so a browser Back after a reload needs two steps. Not looked into; not a board path. Also: after a reload the in-app navigation ids restart at 1 while older browser history entries keep their old ones, so a stale entry can match a different stack row. Noted, not reproduced as a fault.
